- 片寄りの原因は、line の順番表（スケジュール）にあります。

  - 位置3 を通るのは6つの格子点です。
  - そのため、y方向の結合は、片方の橋に 6、もう片方に 2 の割合で乗ります（`outputs/b_visits_out.txt`）。
- y方向の結合を橋に均等に割り振る版（`scripts/ising_line_bal.py`）も作りました。
  - 正しさは確かめました（t1 で 7.3e-12、t2 で 4.5e-14、`outputs/b_out.txt`）。

## 4. 言えること・言えないこと

### 言えること

1. line は、fold と同じ量子ビットと結合を使い、CZ は46%少なく、層の数と長さはほぼ同じで、待ち時間の平均は約1.5倍です。
2. line は、y方向の結合を、行0 と行1 の間の2つの橋に 6:2 で乗せます。これは順番表から来る構造的な片寄りで、橋 q16（場所1 では q17）の CZ は 72 になり、fold の 48 の1.5倍です。
3. 実機での line の悪化は、場所0 の t2〜t4 で、橋 q16 のまわりの3つの格子点（13〜15）にほぼ集中しています。そこの物理量子ビット（q20、q23）は、line の腕で往復の値が低くなっています。
4. FakeFez の模型（ゲート誤差、T1・T2、読み出し、2025-02 の値）では、line は fold より正解に近くなります。悪化の場所も、実機と一致しません。

### 言えないこと

1. **なぜ実機で line が遠かったのかは、わかりません。**
   - 模型に入っている雑音だけでは、実機の向きは出ませんでした。CZ が減った分だけ良くなる、という結果です。
   - なので、実機の差は、模型に入っていない何か（当日の較正の違い、待ち時間中の雑音、橋への CZ の集中、1回きりの揺れのどれか、または組み合わせ）から来ているかもしれません。しかし、どれなのかは、今のデータでは切り分けられません。
2. 橋 q16 への CZ の集中が原因だとは言えません。
   - 模型では、集中があっても line の方が近くなっています。
   - ただし、模型の (3, 16) の誤差は小さく（0.0042）、当日の値は持っていません。
3. 待ち時間が長いことが原因だとは言えません。
   - 模型は待ち時間の T1・T2 の減衰を入れていますが、それでも line が近くなりました。
   - 隣どうしの ZZ の漏れ（クロストーク）は、模型に入っていません。
4. 実機の結果が、もう一度流しても出るかはわかりません。4×3×2 の実機は1回だけで、別の日の繰り返しはありません。
5. シミュレータは場所0 だけです。場所1 は流していません。指示書は両方の場所でしたが、1回目の見積もりが甘く、時間の上限内に収めるために減らしました。

## 5. 確かめるための実機の試験の形（案。宣言の材料）

どの案も、決めるのはオーナーです。私は IBM にはつないでいません。

1. **同じ回路の繰り返し**
   - 4×3×2 の場所0 と場所1 の fold と line を、別の日に、そのまま流し直します。
   - 「line が遠い」が繰り返し出るかを見ます。いちばん安い試験です。
2. **待ち時間の雑音を抑える**
   - line の待ち時間に、動的デカップリング（何もしていない量子ビットに打ち消しのパルスを入れる）を入れた腕を加えます。
   - DD ありとなしで line − fold の差が変わるかを見ます。
3. **橋の片寄りの試験**
   - 位置7 を4つの格子点が通る順番表を探し直して、橋の CZ が 48 / 48 になる line を作ります。順番表の探し直しは、まだやっていません。
   - 今の line と、新しい line を並べて流します。
4. **当日の較正での模型**
   - 実機を流した日の較正（BackendProperties）を保存しておき、`expsim.py --props` で同じ計算をします。
   - 「当日の較正の違い」で説明がつくかどうかを、模型の側から見ます。調整はしません。
