## Question

On a device, without mitigation, does the folded formula placement (psf-os grid3d v3) of a 4 x 2 x 2 cubic-lattice
kicked Ising (16 sites) read the exact answer as well as, or better than, the same circuit routed by Qiskit's SABRE?

## Problem and answers

- 4 x 2 x 2 cubic lattice; each step RZZ(-pi/2) on every lattice edge, then RX(0.8) on every site; Z readout of every
  site; t = 1, 2, 3.
- Exact answers by statevector (`grid3d.exact`), in the file the builder writes (`ANSWERS_OUT`, tags g3d_t<t> and
  sabre_t<t>), **SHA-256 6b2d068c7dfb4bf62b4d7bc2df2a42b5a013e2520c8b2acc009d7c982e05a816** (the same bytes on every
  device: the answers do not depend on the device). The file is committed after the verdicts.

## Arms (one job per device, the same device for both)

- **A, v3 fold:** psf-os `grid3d.prepare(..., layout="fold")` (psf-os e5f95b5): the first translation in the fixed
  order that touches no failed element and uses couplers only; floor and mirror as in 2D, mirror from the compiled U.
- **B, SABRE:** Qiskit's SABRE layout and routing on the record's coupling graph without failed elements,
  `seed_transpiler = 0` only (choosing a best seed would be a search); RZZ(+-pi/2) as one CZ as in A; floor and
  mirror the same way.
- Both read only the device record (coupling graph, failed marks); no calibration number; no correction, no
  mitigation.
- Job: 2 arms x 3 depths x (circuit, floor, mirror) + the ring sentinel = 22 circuits, 4000 shots, built by
  `gpu/os3d_compare_build.py` at this commit (dry run on the fez record of 11-05: 27.6 s by the model).

## Devices

- The devices of the night's daily record (`prereg/daily/standing_rules.md`: the queue read right before the fetch,
  every device with at most 10 pending jobs, else the one with the fewest), from the same fetched records.
- A device on which A finds no qualifying translation, or the job is refused by the time model, gets the 3D test
  recorded as not run there (a line, with the reason); nothing else is tried on it.

## Procedure

1. Fetch (the daily record's fetch; VPN OFF). 2. Build with `gpu/os3d_compare_build.py DEVICE_RECORD OUT ANSWERS_OUT`;
   the printed answers SHA-256 must equal the one above, else stop. 3. Submit (the job's own device). 4. Right after
   the submit: `gpu/calib_beside.py RUNS OUT/CALIB_BESIDE_submit.json --backend DEVICE`. 5. Collect; then
   `gpu/calib_beside.py RUNS OUT/CALIB_BESIDE_run.json --backend DEVICE --job JOB_ID`. 6. Score with
   `gpu/os3d_score.py OUT ANSWERS_OUT` (at this commit); commit the scores; then the answers file.

## Judged (per device; `gpu/os3d_score.py`, fixed with this file)

- Per arm and t: **READS** (MSE <= half the mean square of the exact values), **AGREES** (|M - M_exact| <= 0.05),
  **BEATS** (MSE below the better of all-0 and all-1) (`gpu/practice_score.judge`, unchanged).
- Per t: **R = MSE_A / MSE_B: HELPS if R <= 0.8, HURTS if R >= 1.25, NO EFFECT between.**
- Reported beside, not judged: retention M / M_exact, the normalised error, the share within 2 SE, CZ and CZ layers
  of each arm, the floor and mirror means, the sentinel; per arm the worst and median CZ and readout errors of its
  elements at the submit and at the run (`gpu/calib_beside.py`, owner's decision 2026-11-06 06:28 CET; report only,
  never fed into a build, a placement or a score), with any missing or non-operational element named.

## Recorded

- `results/os3d-device-2026-11-06/<device>/` (device record, job, counts, CALIB_BESIDE files, scores), and a line per
  device in its README: successes and failures alike.

## Expectation (simulation only; not evidence about a device)

Uniform depolarizing model: R 0.72 / 0.76 / 0.75 at t 1 / 2 / 3 (HELPS). FakeFez with its dead couplers marked:
0.58 / 0.59 / 1.27-1.30 (t 3 HURTS over six trajectory seeds). So HELPS is expected at t 1 and 2; t 3 is open.
AGREES is unlikely for either arm (signal loss 5-8 % of M_exact). On a device a bad coupler the record does not mark
failed can decide the comparison for either arm; the calibration beside is there to show it.

## Limits

One small lattice (16 sites); one or a few devices on one night; one seed of SABRE (another seed can differ by
10-20 % in CZ). All answers are classically computable; no advantage is claimed.
